# Notifyi 디지털 트윈 개발 계획: 실물 동기화와 조립판 검증

작성 기준: 2026-10-05. 이 문서는 **개발 계획**이며, 실물 모터 구동 승인이나 안전성 검증 결과가 아니다. 현재 작업 중인 파일을 덮어쓰지 않도록 계획만 별도 파일로 기록했다.

## 결론

가장 먼저 만들 기능은 **삼성 노트북의 실제 모터 상태를 읽기 전용으로 3D 화면에 반영하는 것**이다. 화면의 각도로 모터를 움직이는 기능은 그다음 단계다. 현재 예제 조립은 STEP 검사에서 A축 ±30° 간섭이 확인됐으므로, 해당 배치를 구동 테스트에 사용하면 안 된다. 읽기 전용 연동을 하더라도 화면이 실제 하중·충돌·안전 운용각을 보증하는 것으로 표현하지 않는다.

| 단계 | 화면에서 보이는 것 | 실물에 보내는 것 | 시작 조건 |
| --- | --- | --- | --- |
| 현재 | 수동 스캔 시점의 ID·위치·토크 ON/OFF·오류 | 스캔을 위한 읽기 패킷만 | 메인 제어 중지, OpenCR/포트 연결 |
| 1차 목표 | 최신 위치를 따라 움직이는 3D 모델, 시각·신선도·오류 표시 | 상태 읽기만. 토크·목표 위치 쓰기 없음 | A/B축↔실물 ID 및 부호 확인, 포트 단일 소유 |
| 후속 목표 | 사용자 요청 목표와 **실제 읽은 위치**를 별도로 표시 | 제한된 목표 위치 명령 | 전체 가동 경로·기계적 한계·정지/고장 대응 검증 |

달력 날짜를 기준으로 구동 연동을 약속하지 않는다. 1차 목표는 아래 P0 완료 조건을 통과하면 개발할 수 있다. 후속 목표는 실물 검증에 따라 범위를 다시 정한다.

## 현재 구현과 정확한 한계

- [`serve.py`](serve.py)는 시리얼 포트를 열지 않고 `data/connection_status.json`을 읽는다. 수동 스캔은 15초가 지나면 오래된 검사로 취급한다. 메인 제어가 **멈춘 상태**에서만 [`watch_dynamixel.py`](../../scripts/watch_dynamixel.py)가 시리얼 읽기와 상태 파일 갱신을 반복할 수 있다. 관측기를 종료하거나 파일 갱신이 끊기면 화면은 오래된 관측으로 전환한다. 실물 하드웨어에서의 장시간 운용 검증은 아직 하지 않았다.
- [`scan_dynamixel.py`](../../scripts/scan_dynamixel.py)는 ID를 찾고 위치·토크 활성 여부·하드웨어 오류를 읽어 상태 파일로 저장할 수 있다. 메인 제어와 동시에 같은 `/dev/ttyACM0`를 열어서는 안 된다.
- [`joint_writer.py`](../../src/robot/joint_writer.py)의 `read_positions()`는 메인 제어가 소유한 포트에서 ID 2~7의 현재 위치를 읽을 수 있다. 그러나 현재 브라우저용 연속 상태 게시 경로는 없다.
- [`config/robot.yaml`](../../config/robot.yaml)은 OpenCR 브리지 `/dev/ttyACM0`, 57600bps, 프로토콜 2.0, 활성 ID 2~7을 지정한다. [`config/joints.yaml`](../../config/joints.yaml)은 ID별 zero·방향·상대 범위를 갖지만, 이는 **현재 설정값**이지 새 구조의 모든 실제 간섭·하중 검증 결과가 아니다.
- 3D 모델 하나는 2XL의 A/B 두 축을 표현하지만, 어느 실물 ID 두 개가 같은 하우징에 들어 있는지는 화면에서 사용자가 직접 배정한다. 기본값은 미배정이다. 이 배정을 검증 없이 추론하거나 6개 ID를 곧바로 6개 하우징으로 생성하면 안 된다.
- 브라우저의 A/B `−90°~+90°`는 미리보기 제한이다. 실물 ID별 운용 범위와 연결되지 않는다. 조립 상태 안내도 일부 알려진 STEP 예제에 대한 분류이며, 모든 부품 쌍의 자동 충돌 검사기가 아니다.

## P0 · 읽기 전용 실물 동기화

### 1. 물리 매핑을 먼저 기록

삼성 노트북에서 각 하우징의 A/B축이 각각 어떤 ID인지 확인해 매핑표를 남긴다. ID 1·8은 현 설정에서 유휴다. ID 2~7은 하우징의 물리 위치, A/B축, 정방향, zero tick, 현재 동작 모드를 각각 확인한다. **토크를 켜지 않고** 수동 이동에 따른 위치 변화를 관찰하는 절차부터 시작한다. ID 5·6처럼 zero 부근이 0/4095 경계를 걸칠 수 있으므로, 단순 뺄셈 대신 한 바퀴 감김을 고려한 각도 차이와 원시 tick을 함께 기록한다. 전원 재인가·토크 인가·동작 모드 변경 후 값의 연속성이 바뀔 수 있으므로 재확인 상태를 따로 둔다. [ROBOTIS 2XL430 제어표](https://emanual.robotis.com/docs/en/dxl/x/2xl430-w250/)는 Present Position(132)의 리셋 조건을 명시한다.

완료 조건: 한 하우징의 A/B축을 손으로 **각각** 움직였을 때 대응 ID 하나만 예상 부호로 변하고, 화면의 해당 축도 같은 방향으로 변한다. 확인하지 못한 축은 `미배정`으로 남긴다.

### 2. 시리얼 포트 소유자를 하나로 제한

메인 제어가 꺼져 있을 때만 진단용 읽기 전용 폴러가 포트를 소유한다. 메인 제어가 켜져 있으면 그 제어 루프가 이미 읽은 상태를 게시하게 만들고, 별도 폴러는 실행하지 않는다. 웹 서버는 계속 **시리얼 포트를 열지 않는다**. 첫 구현은 동일 노트북의 로컬 상태 파일/API로 충분하며, 맥에서는 기존 SSH 터널로 삼성 노트북의 서버를 본다. 외부 네트워크 공개나 브라우저의 모터 직접 접근은 범위 밖이다.

게시 데이터의 최소 항목: `source`, `observed_at`, `sequence`, `port`, `baudrate`, `protocol`, `id`, `raw_position_tick`, `normalized_tick`, `torque_enable`, `hardware_error`, `operating_mode`, `valid`. 수신 화면은 `관측 시각`, `데이터 나이`, `응답 없음`, `매핑 미확인`을 분리한다. 이전 관측값을 현재 위치처럼 표시하지 않는다. 샘플링 주기는 버스 지연을 측정한 뒤 정하고, 예컨대 10Hz를 처음부터 보장한다고 가정하지 않는다.

완료 조건: 정상 상태에서 화면 위치가 수동 이동을 따라가고, USB 분리·프로세스 종료·ID 미응답 시 지정된 시간 안에 `연결 끊김/관측 중단`으로 바뀐다. 데이터가 끊기면 마지막 자세를 유지하되 **오래된 값임을 명확히 표시**한다. 어느 실패도 토크/목표 위치 쓰기로 이어지지 않는다.

### 3. 동기화 모드와 저장값 분리

화면에 `시뮬레이션`과 `실물 읽기`를 명확히 구분한다. 실물 읽기에서는 관측 자세와 화면에서 편집한 가상 자세를 다른 색/레이어 또는 전환 상태로 보여준다. 자동 저장 JSON에는 조립 구성과 ID 매핑만 보존하고, 순간적인 관측값은 복원 가능한 조립 자세로 저장하지 않는다. 메인 제어의 명령 목표값, 버스에서 읽은 실제값, 화면 편집값을 같은 필드로 합치지 않는다.

완료 조건: 새로고침/JSON 불러오기/네트워크 지연 뒤에도 과거 관측값이 실물 현재값처럼 재생되지 않는다. 읽기 모드에서는 버튼·드래그가 실물에 명령을 보내지 않는다.

## P1 · 조립판의 남은 검증 과제

1. **CAD 신뢰도:** 제공된 `2XL-430.stp`와 이전 `2XC-430.stp`가 동일한 점을 확인해야 한다. 실제 사용 부품의 공식 CAD/실측 치수, 혼·아이들러·판·나사·스페이서·케이블 출구를 한 좌표계에 놓고 기준점/변환 행렬을 기록한다. 현재 [`CAD_FIT_AUDIT.md`](CAD_FIT_AUDIT.md)는 +Z면 홀 정렬과 특정 예제 ±30° 간섭만 입증한다.
2. **체결 판정 범위:** 현재 `미검증/체결 불가/부분 확인·간섭 확인`은 전역 문구에 가깝다. 브라켓 인스턴스별 `체결 홀`, `정적 간섭`, `회전 스윕`, `배선 여유`를 각각 `확인/미검증/실패`로 표시한다. 확인하지 않은 다른 면에 예제 결과를 전파하지 않는다.
3. **가동 범위:** 시뮬레이션 ±90°와 `config/joints.yaml`의 임시 운용 범위를 분리한다. 실제 가동 범위는 각 ID/조립 버전별 도면 스윕·실물 끝각·하중 결과에서만 확정한다. 특히 0°에서 안 겹친다고 중간각이 안전하다고 판단하면 안 된다. `Present Load`도 실제 토크 센서값으로 해석하지 않는다. [ROBOTIS 2XL430 문서](https://emanual.robotis.com/docs/en/dxl/x/2xl430-w250/) 역시 이를 추정값으로 설명한다.
4. **회전 기준 회귀 검사:** X→Y→Z 본체 배치와 A/B 로컬 관절 회전을 분리한 상태를 유지한다. 90° 눕힌 기준 모터에서 하위 모터 두 개를 잇는 경우까지 축 중심, 혼·아이들러 접촉, 연결된 자식의 상대 자세가 변하지 않는지 자동 검사한다. 최소 예제 3개를 JSON으로 고정해 회귀 테스트한다.
5. **조작성:** 모바일에서는 상단 도구를 가로 스크롤로 정리했지만, 도구 발견성·부품 목록/검사 패널 열고 닫기·터치 회전 핸들의 오조작은 실사용 검증 전이다. 데스크톱과 390px 화면에서 `선택→체결→회전→해제→되돌리기` 작업을 직접 수행해 클릭 수, 겹침, 가려진 부품을 점검한다. 필요할 때만 작은 패널을 펼치고 3D 뷰를 우선한다.
6. **상태 표시:** 화면상의 케이블, OpenCR USB 장치 경로, ID 응답, 현재 위치, 하드웨어 LED·전원 상태를 같은 `연결됨`으로 묶지 않는다. 확인 방법과 측정 시각을 각 표시 옆에 둔다. 보드 전류·LED가 API에 없다면 추정 표시를 만들지 않는다.

## P2 · 실물 구동 연동을 시작하기 위한 게이트

아래가 모두 충족되기 전에는 브라우저에서 목표각을 모터에 보내는 기능을 넣지 않는다.

- 실제 하우징/축/ID/부호/zero/동작 모드가 검증되고, 변경 시 재검증한다.
- 나사·스페이서·케이블과 책상/노트북까지 포함해 **전체 후보 경로**의 정적·동적 간섭과 ID별 기계적 한계를 확인한다. 현재 +Z/A 예제의 ±30° 간섭은 먼저 재설계한다.
- 낮은 속도와 제한된 이동량에서 한 축씩 시험하고, 전원·통신·과부하·위치 읽기 실패·토크 해제 시 구조물 낙하를 다룰 정지 절차를 문서화한다.
- 명령은 모터 담당 프로세스 한 곳만 실행하고, 서버/브라우저는 요청 인터페이스만 쓴다. 명령 시점에 매핑, 모드, 현재 위치, 운영 범위, 요청 유효기간을 다시 검사한다. 실패·취소·실행 시작·실제 도달을 구분해 기록한다.
- 버스 워치독과 하드웨어 오류를 다룰 정책을 실물에서 검증한다. 워치독은 통신 단절 시 정지 보조 수단이지 브라켓 충돌·자중 낙하를 막는 장치가 아니다. [ROBOTIS 2XL430 Bus Watchdog](https://emanual.robotis.com/docs/en/dxl/x/2xl430-w250/#bus-watchdog98).

첫 구동 데모의 완료 조건은 **한 축, 무부하 또는 안전하게 지지한 상태, 작은 검증 각도**에서 요청·실제 위치·정지·오류가 모두 기록되는 것이다. 그 뒤에도 다축·탁상 배치 전체로 바로 확장하지 않는다.

## 추천 구현 순서

1. 물리 A/B축↔ID 매핑표와 실물 조립 버전 고정.
2. 삼성 노트북의 메인 제어 중지 상태에서 읽기 전용 관측기와 stale/오류 UI를 실물로 검증. 메인 제어 중 관측값 게시 경로는 별도 구현.
3. 실제 각도로 3D 모델이 따라오는지 한 하우징부터 검증.
4. 브라켓별 CAD 체결·회전 스윕과 조립판 판정 정확도 개선.
5. 모바일/데스크톱 조작 작업 테스트와 회귀 JSON 확대.
6. P2 게이트를 통과한 축만 별도 실물 구동 실험.

**이번 계획 작성은 코드의 모터 제어 경로, 설정값, 실제 모터 상태를 변경하지 않는다.**
